## 全体雑感

AIという言葉が指す範囲は色々あるが、やはりLLM活用によるAI支援開発による環境の変化に関する発表が多かった。
私個人としては生成AIに関する強い認識として以下4点が、OpenAIが台頭してきた生成AI普及当初からある。これらはずっと変わっていない。

- A: 生成AIは人類に短期的に利益をもたらし、長期的に不利益をもたらす
- B: 生成AIはどこまで性能が上がっても道具に過ぎず、責任は道具を使った人間のもの
- C: 生成AIは人間の作業を拡張するが、能力を拡張しない
- D: 生成AIは（人間が最もAIに代わって欲しかった）物理的雑務を代わってくれない

Dは半分ジョークだが、半分は真面目な話で、知的労働を全て生成AIに委譲すると人間は物理作業だけやる奴隷になりかねないという観点を含んでいる。
認知負債の話はAとBに関連していて、本来能力が足りておらず説明できないシステムもAIで作れてしまう。これは「作れていない」のに「作れている」と認識してしまう点に課題があるのだと思う。それが長期的に不利益をもたらす。
もちろん「作れている」の定義自体が動いている、という捉え方もある。とりま動けばいい（後のことは後で考えればいい）というのはその一例である。ビジネスで許される姿勢だとは思わないが、そのラインも人間が決めることなのだろう。
守りたい性質やレビューの話、コードを読むかの話などはBとCに関連していて、AIで加速した開発を全てレビューするのは非現実的だし、精神的にも負担が大きく、集中力というリソースにも限界がある。その拡張されない人間の能力とリソースの中で責任を負う品質をどう確認・担保するかという組織的な現実解をどう探っていくかの話。
キャリア中心の話や組織設計の話などはどれとも浅く関係している気がするが、少し軸が違う話と整理した方が良い気がする。生成AIを背景として働き方にフォーカスした話は、そちらが主役。
OSSメンテナの話はBとCに関連していたが、Aにも少し関わっていそうな気がしつつ。

生成AIでいかに高品質なものを出力するか、それをどう検証するか、それは人間が見なくても品質を担保できるか、という話とほぼイコールの文脈で、システム的品質（技術負債）の話もあれば、未理解（認知負債）の話もあり、説明責任（意図負債）の話もあった、という整理の仕方もある。そう整理すると、みんな生成AIが出力した内容の品質と負債に悩んでいるのである、と総括することも、できるのかも。

少しだけ残念だったのは「何をAIに読ませていいのか」みたいな話に踏み込む発表がなかったなと。まあでもケースバイケースで触れようがないし、発表として面白くならない気もするね。

  - 意図を後から回復するのは難しく、ときには不可能になる
  - AIエージェントが能動的参加者になったことで緊急性が増した
    - AIは書かれた意図しか読めないため、意図が残っていないとAIは誤った目的に最適化する
    - AIはもっともらしく行間を埋めてしまうため、人の判断と見分けがつきにくい
    - AI支援開発により、意図を記録できる瞬間を逃しやすくなった

  - 理解せずとも計測できる指標（例えばDORAメトリクス）を上げられる
  - 生産性を上げたい組織と個人の共犯関係が成立してしまう
    - 人事評価制度のアップデート（インセンティブ変更）が急務となるが、測れない問題に対処しなければならないため、手強い。

  - 熟慮（システム2）は直感（システム1）が「何かおかしい」と摩擦を検知したときに起動する
    - AIの流暢で自信ありげな出力はその摩擦を起こさず、疑いが起動しにくくなる（流暢性のヒューリスティック）
    - 人間の自信は（AIが間違っていても）上がる。だから本人には認知的降伏が自覚できない。

  - AIにクイズを作らせる
  - 図や画像など豊かな仕組みでAIに説明させる

  - どうやったら理解が足りないことに気付けるか
  - If you want to master something, teach it. (Richard Feynman)

## AIが生成したコードは読むべきか？ DMM.com

ミノ駆動がハンネらしい。
システム開発の基本を噛み砕いて説明しているだけなのに、AI時代に刺さる内容がピックアップされている。最後のまとめであった通り、どの考え方も20世紀後半に生まれた概念。
しかしサボらず要件を設計しようねという話になると、AI駆動開発のメリットを失うことにもなりそう。
契約自体をAIに書かせれば、人間はそれを確認するだけでいい。しかし確認コストが…確認しないためには…
入れ子になった？ しかし重要な基礎概念ではある。

### メモ

- 抽象化設計とコードの品質保証
- 物議を醸している話題
  - 読んで理解しないと責任取れない、デバッグできない
  - 品質保証する仕組みを作って読まなくてよくする
    - ハーネスエンジニアリングとか
- 全く読まなくて良い、にはならない。ただ読む必要性や労力は低減できる
- 重要なポイント
  - 契約による設計
  - 副作用のない関数
  - 抽象化
- AIコードの課題
  - 責任所在
  - もっともらしいがよく読むと問題のあるコード
  - 脆弱性
  - 非機能要件
  - 古い書き方
  - ポリシーに合わない書き方
  - 期待する正しい結果が得られるかわからないコード
- **契約による設計**
  - バートランド・メイヤー氏が考案した設計手法
    - 事前条件、事後条件、不変条件を定義する
  - 契約とは、呼び出し側と関数側の間の約束
    - 条件を守って呼べば、期待する結果を返す
  - 例：BMI
    - 事前（実行前）条件：身長が0より大きく3以下、体重が0より大きく700以下
    - 事後（実行後）条件：戻り値が `(体重kg) / (身長m^2)` であること
  - 不変条件とは、メソッド実行前〜後まで常に満たすべき条件
  - 契約による設計の３条件は、ブラックボックステストの基準にもなる
- **副作用のない関数**
  - 副作用があると実装を直接読む必要が出てくる
    - インスタンス変数の変更
    - グローバル変数の変更
    - 参照型変数の変更
    - DB操作やIO操作など
  - 副作用を隔離した上で、可能な限り副作用のない純粋関数を多く設計すること
    - immutableなオブジェクトも重要
- **抽象化**
  - 制御抽象化：条件分岐、ループ処理、サブルーチン、関数などの方法で制御を構造化する
  - データ抽象化：データ構造と操作方法をまとめて型として定義する
  - 適切に抽象化すると中身を気にせず使える
  - 「中身を気にしなければ信頼できないコード」は「AIのよくわからないコード」に通じる
- 信頼できるコードを実装させるには
  - 契約による設計、副作用隔離、クラス仕様をテストコードでカバーする
- **AI時代でも基本しか勝たない**
  - AIツールの使い方を覚えるのはほどほどにして、増幅元である人間の能力をきちんと高めましょう

## AIがコードを書く時代に、OSSメンテナは何をしているのか mattn

自分も小規模ながらOSSオーナー（メンテナ）をしていたので、興味のあったテーマ。
結局は責任の話になるのである。そしてやっぱり重くなっているんだなあと。
さらっと触れて流したゴミPRラッシュの話が、そうだよねって感じで苦笑いポイント。現場でも起きるからなあ。

### メモ

- 何が変わったか：現在地
  - コードを書くコストがほぼゼロになった
  - ライブラリを探すよりAIに書かせた方が早い場面も増えた
  - では、**OSSはもう要らないのか？**
- OSSメンテナ側で起きていること
  - AI生成のパッチ、Issue、脆弱性報告が押し寄せる
  - 一見それっぽい、でも中身を読むと壊れている、ということが頻繁にある
  - curlやvimプロジェクト等はAI生成のゴミ報告に公式に苦言を呈した
  - 書くコストが下がった分だけ、**読む側・判断する側のコストが跳ね上がった**
- AIが書くコードはOSSを学習して生まれている
  - AIが生成したコードも結局OSSライブラリをimportしている
  - 依存の連鎖の一番下には、今日も人間のメンテナがいる
  - OSSが止まればAIの出力も古びていく
- 人間に何が残るか
  - マージするかどうかは人間が決める
  - コードを「書く」ことと「引き受ける」ことは別物
    - 子犬をプレゼントすることに例えられる
  - メンテナの仕事は**プロジェクトに何を入れないかを決めること**
  - **互換性という10年単位の約束**
    - e.g. go-sqlite3のようなライブラリは無数のプロダクトの土台になっている
  - 何を機能として持ち、何を持たないか - プロジェクトの輪郭を決めるのは思想
    - AIは平均的な正解を出す。**尖った判断はしない。**
  - AIにコミュニティ生成はできない
    - OSSはコードの集まりであると同時に、人の集まり
    - issueでの対話、コントリビュータが育つ過程、信頼の積み重ね
    - 育てるのは人間の力量次第
- AIにどう向き合うか
  - AIはOSS活動の敵ではなく道具
  - 早く出せた成果物の賞味期限が伸びる
  - ライセンスと出自には気を配る
  - 「生成」で始めてもいい。でも「継続」は自分の意思で。
- **コードを書くコストは下がった。判断と責任のコストは上がった。**
